# v0.5 — Known Issues & Decisions

---

## output_vars field in sys_flow_context remains empty

### Finding

`sys_flow_context.output_vars` was empty in all test runs in v0.4.
Investigated further in v0.5 — the NowLink Test Subflow has an output variable
(`result`) that is set during execution, but `output_vars` returns an empty string.

Alternate field names tried: `output_variables`, `outputs` — neither exists as a
queryable field on `sys_flow_context`.

Theory: output variable values are stored in the execution plan JSON blob, not in
a flat field accessible via the REST API with standard roles.

### Decision

Accepted as a known limitation. `get_flow_status` returns whatever `sys_flow_context`
provides. If `output_vars` is empty, that's what Claude reports.

Carry forward to v0.6 or v1.0 when there's a clearer path to output variable access.

## flow_designer role required for action discovery

### Finding

`sys_hub_action_type_definition` returned 403 for `nowlink.dev` with only
`rest_service` + `web_service_admin` roles.

Root cause: `sys_hub_action_type_definition` inherits from `Application File`
base class. `Application File` carries a read ACL requiring `flow_designer` or
`admin`. This is the same base class used by scripts, business rules, and other
platform code artifacts.

By contrast, `sys_hub_flow` (subflows/flows) inherits from `Flow Block`, which
has no equivalent restriction. This distinction is intentional ServiceNow design.

`sys_db_object` comparison:
- `sys_hub_flow` → `super_class: Flow Block` → readable with `rest_service`
- `sys_hub_action_type_definition` → `super_class: Application File` → requires `flow_designer`

### Decision

Add `flow_designer` to `nowlink.dev` on the PDI. This is acceptable for development.

For production: evaluate per security policy. `flow_designer` grants read access
to all Flow Designer metadata tables — scripts, business rules, actions, etc.
It's a developer role, not an integration role. Some organisations may not be
comfortable granting it to an integration user.

NowLink documents this as a requirement for action tools. `list_actions`,
`describe_action`, and `trigger_action` include a note in their tool descriptions
that `flow_designer` role is required.

## Flows cannot be triggered via API — except record-triggered ones

### Finding

v0.4 proved that calling the bridge `/trigger-flow` with `flow_name` + `table_name`
+ `sys_id` fails with 500 if the flow expects inputs in the exact trigger shape it
normally receives from the platform.

Further investigation in v0.5: `label_cache` reveals the trigger context.
Record-triggered flows have variables labelled `"Trigger - Record Updated➛..."` or
`"Trigger➛..."` with a `reference` field pointing to a table. These can be triggered
via the bridge by passing the table name and a record sys_id — the bridge fetches
the GlideRecord server-side and passes it as `current`.

Non-record flows (scheduled, application trigger, SLA trigger) have no record
context variable. There is no sensible way to call them via API.

### Decision

`trigger_flow` tool detects the trigger type:
- Record-triggered → accepts optional sys_id, triggers via bridge if provided
- Non-record → returns explanation, suggests rebuild as Subflow

The `/trigger-flow` bridge endpoint is now used in production (previously installed
but unused).

## Native flow_api REST endpoint not used

### Finding

`POST /api/now/flow_api/flows/{id}/run` — this is the native ServiceNow REST
endpoint for triggering Flow Designer flows. It would be cleaner than the bridge.

However, it requires Integration Hub Enterprise to be active. On a standard PDI
it returns 400. The bridge is the correct solution for standard instances.

### Decision

Continue using the bridge. For v1.0: detect whether `flow_api` is available
by attempting a known-safe call, and use it if so, fall back to bridge if not.
This would make NowLink work better on Enterprise instances without requiring
code changes from the user.

## Duplicate tool registrations were silently ignored by Python

### Finding

`server.py` had the three v0.4 flow tools (`list_subflows`, `trigger_subflow`,
`get_flow_status`) defined four extra times — 420 lines of copy-pasted dead code.
Python silently accepts duplicate function definitions at module level; the last
definition wins. The earlier ones were unreachable. FastMCP registered only the
last definition.

This was introduced during v0.4 development and never caught because the server
worked correctly (the last definition was the right one).

### Decision

Removed all four duplicate blocks. Added `tests/test_server_structure.py` which
uses Python `ast` to parse `server.py` and assert that every `@mcp.tool()` function
is defined exactly once. Also asserts an exact tool count — when new tools are added,
the test fails with a clear message to update the count. This forces awareness of
what's registered.

## trigger_flow tool description is load-bearing

### Finding

First implementation of `trigger_flow` was a pure fallback — it always explained
why flows can't be triggered. The tool description said it was for "explaining why
flows cannot be triggered."

When the smart trigger logic was added (inspect trigger type, trigger if
record-based), Claude still called `describe_flow` first because that tool's
description said it was for "understanding how flows work." `describe_flow` returns
`can_trigger_via_api: False` — Claude saw that and stopped without calling
`trigger_flow`.

### Decision

Added to `trigger_flow` docstring: `ALWAYS use this tool when the user asks to
trigger a flow — do NOT call describe_flow first. This tool handles the full logic
internally.`

Added to `describe_flow` docstring: `Do NOT use this tool when the user asks to
trigger a flow — use trigger_flow instead.`

Lesson: tool descriptions are executable instructions, not passive documentation.
Claude routes based on them. A single sentence change to a docstring changed
observable tool call behaviour.

## Trigger label format has two variants

### Finding

Flow trigger variables in `label_cache` have two label formats:
- `"Trigger➛Task SLA Record"` — direct trigger variable (no trigger type specified)
- `"Trigger - Record Updated➛Versions Record"` — includes trigger type in label

Initial `describe_flow` implementation used `startswith("Trigger➛")`, which
correctly matched the first format but missed the second. This meant record-triggered
flows using the dash format returned empty `trigger_context`, causing `trigger_flow`
to incorrectly classify them as non-triggerable.

Discovered via tests: `TestFlowTriggerContextParsing.test_record_trigger_extracted`
failed because test data used the dash format (copied from real PDI data), but
the parser only matched the no-dash format.

### Decision

Fixed filter: `label.startswith("Trigger") and "➛" in label and label.count("➛") == 1`

The `count("➛") == 1` check excludes nested trigger path variables like
`"Trigger - Record Updated➛Versions Record➛Document"` which are sub-fields of
the trigger record, not the top-level trigger context.

Note: the test failure found a real production bug — the `Review and Approval
Workflow for Document Version` flow uses the dash format and would have been
incorrectly classified as non-triggerable without this fix.
