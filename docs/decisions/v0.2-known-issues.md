# v0.2 — Known Issues

## create_record reports timeout even when the write succeeded ✅ Fixed in v0.2

**Fix:** `create_record` now catches `httpx.TimeoutException` and calls `_verify_create`
before reporting failure. Queries for a matching record created within the last 2 minutes.
If found — returns success. If not found — raises a clear error.

---

## update_record reports timeout even when the write succeeded ✅ Fixed in v0.2

**Fix:** `update_record` now catches `httpx.TimeoutException` and calls `_verify_update`
before reporting failure. Re-fetches the record by sys_id and compares submitted field
values against current ServiceNow state. If all fields match — returns success.
If any field didn't apply — raises a clear error with the list of mismatched fields.

Note: fields recalculated by business rules (e.g. priority derived from impact+urgency)
may show as mismatches even though the write was correct — the business rule overwrite
is ServiceNow's logic, not a NowLink failure.

---

## REQUEST_TIMEOUT was a hardcoded constant ✅ Fixed in v0.2

**Fix:** `REQUEST_TIMEOUT` now reads from `NOWLINK_REQUEST_TIMEOUT` in `.env`,
defaulting to 60 seconds. Documented in `.env.example`.

---

## TABLE_MANDATORY is hardcoded — breaks on custom tables

**Symptom:** `create_record` on a custom table (e.g. `u_my_table` extending `task`)
passes mandatory field validation even without `short_description`. The POST goes out,
ServiceNow rejects it with a validation error. NowLink surfaces that error but the
pre-flight validation should have caught it before the write.

**Root cause:** `TABLE_MANDATORY` only covers six known standard tables. For unknown
tables, validation falls back to `sys_dictionary` queried for `name={table}`, which
returns only fields defined directly on that table — not inherited ones. Custom tables
extending `task` inherit `short_description` and other mandatory fields that are
invisible to this query.

**Impact:** Pre-flight validation is incomplete for custom tables. Writes still fail
safely (ServiceNow rejects them), but the error message comes from ServiceNow rather
than NowLink's validator, and is less clear.

**Fix planned (v0.3):** Replace `TABLE_MANDATORY` and the `sys_dictionary` fallback
with a dynamic `get_mandatory_fields(table)` function that walks the full inheritance
chain via `sys_db_object` and queries `sys_dictionary` with the complete ancestry list.
Works for any table on any instance. `TABLE_MANDATORY` will be removed entirely.
See `docs/decisions/v0.3-open-questions.md` for full design.
