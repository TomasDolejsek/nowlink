# v0.1 — Known Issues

## describe_table shows sys_dictionary view, not NowLink's curated allowlist view

**Symptom:** `describe_table` on `incident` returns ~21 fields — the incident-specific
fields from `sys_dictionary`. Inherited `task` fields (`short_description`, `state`,
`priority`, `assigned_to`) are missing because they live under `name=task` in
`sys_dictionary`, not `name=incident`.

**Why this is probably fine:** Walking the full parent chain would return 200+ fields,
which defeats the point of the shaper. The inherited fields that actually matter are
already in the shaper's allowlist and get returned correctly by `query` and `get_record`.

**Real issue:** `describe_table` currently shows what ServiceNow's schema looks like,
not what NowLink will actually return. These are two different things. A user asking
"what fields does the incident table have?" probably wants to know what NowLink gives
them — which is the allowlist, not `sys_dictionary`.

**Fix to consider (v0.2):** For tables with a known allowlist in `shaper.py`, return
the allowlist fields with their types rather than querying `sys_dictionary`. Fall back
to `sys_dictionary` only for unknown tables. This gives Claude an accurate picture of
NowLink's actual output.

## Required roles for nowlink.dev not obvious from ServiceNow documentation

**Symptom:** `rest_service` alone is not enough to query ITSM tables or `sys_dictionary`.
Took trial and error to identify the full required role set.

**Roles required and why:**
- `rest_service` — baseline for OAuth token and API access
- `itil` — read access to incident, problem, change, task and related ITSM tables
- `personalize_dictionary` — read access to `sys_dictionary` (needed for `describe_table`)

**Fix:** Document in README and setup guide. Consider adding a `nowlink check-roles`
CLI command in v0.2 that verifies the integration user has all required roles.
