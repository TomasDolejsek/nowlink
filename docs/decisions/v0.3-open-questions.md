Starting point for v0.3 (Safe Bulk). Everything here is either unresolved from
a previous version or a new design question that needs answering before or during
the build.

**Plan:** Add `NOWLINK_SSL_VERIFY` to `.env` defaulting to `true`. Add `--no-verify`

### No refresh_token flow (from v0.0)

**Status:** Still open.
**Current behaviour:** On token expiry, NowLink does a full re-auth using
username + password. Correct but inefficient — full re-auth every 30 minutes.
**Plan:** Store the `refresh_token` from the initial token response in the keychain.
On expiry, POST to `/oauth_token.do` with `grant_type=refresh_token` instead of
`grant_type=password`. Fall back to full re-auth only if refresh fails.

### get_write_log tool (from v0.2 session)

**Status:** Still open.
**Plan:** Add a `get_write_log` MCP tool that reads `~/.nowlink/logs/writes-YYYY-MM-DD.log`
and returns entries as structured data. Should support filtering by date, table, and

### Priority set directly gets overwritten by business rules (discovered v0.2)

**Status:** Documented, no fix needed in NowLink.
**Finding:** On most ServiceNow instances, priority is auto-calculated from impact +
urgency via a priority lookup rule. Setting `priority` directly via PATCH gets
immediately overwritten. Correct approach: set `impact` and `urgency` instead.
**Action:** Document clearly in `update_record` tool description and in README.
Consider adding a note to the `create_record` tool description for incident.

## Mandatory field detection is hardcoded and breaks on custom tables

**Current behaviour:** `TABLE_MANDATORY` in `shaper.py` is a hardcoded dict covering
six known tables. For unknown or custom tables (`u_` prefix), `create_record` falls
back to `sys_dictionary` queried for `name={table}` — which only returns fields
defined directly on that table, not inherited ones. Custom tables almost always extend
`task` or another base table, so `short_description` and other inherited mandatory
fields are invisible to the query. Validation passes, POST goes out, ServiceNow
rejects it.

**Fix planned (v0.3):** Replace `TABLE_MANDATORY` and the `sys_dictionary` fallback
with a dynamic `get_mandatory_fields(table)` function in `client.py`:

1. `get_table_ancestry(table)` — walks `sys_db_object` upward via the `super_class`
   field to build the full inheritance chain (e.g. `incident → task → ...`)
2. `get_mandatory_fields(table)` — queries `sys_dictionary` with
   `nameIN{full ancestry list}^mandatory=true^active=true^elementISNOTEMPTY`
   Returns a `set[str]` of field names that are mandatory anywhere in the chain.

Two API calls per validation. Works for any table on any instance including custom
tables and any admin-configured mandatory fields. Replaces `TABLE_MANDATORY` entirely
— no hardcoded map to maintain.

**Changes required:**
- `client.py` — add `get_table_ancestry()` and `get_mandatory_fields()`
- `safety.py` — update `validate_fields()` to accept `set[str]` instead of schema list
- `server.py` — replace `TABLE_MANDATORY` lookup with `get_mandatory_fields()` call
- `shaper.py` — remove `TABLE_MANDATORY`

## New for v0.3 — Bulk Operations Design Questions

### Session token design

The roadmap specifies: `bulk_preview` generates a session token, `bulk_execute`
requires it, token expires in 5 minutes.

**Questions to resolve before coding:**
- Where is the token stored? In-memory dict on the FastMCP server process is simplest
  (token lives as long as the server process). A file in `~/.nowlink/` would survive
  server restarts but adds complexity.
- What does the token encode? At minimum: the table, the filters, the fields_to_set,
  and the timestamp. Hash of these + a secret? Or a UUID mapped to stored state?
- How does `bulk_execute` verify the preview wasn't tampered with? If the token is
  just a UUID pointing to stored state, Claude can't modify the query between preview
  and execute. If the token encodes the parameters, we need to verify they match.

**Recommendation:** In-memory dict keyed by UUID. Value is `{table, filters,
fields_to_set, preview_count, expires_at}`. Simple, no file I/O, token dies with
the server process (which is fine — user would re-preview anyway after a restart).

---

### Hard limit: 500 records maximum

**Questions to resolve:**
- Where is the count checked — in `bulk_preview` or `bulk_execute` or both?
  Both. `bulk_preview` should refuse to generate a token if count > 500.
  `bulk_execute` should re-check before writing (count could theoretically change
  between preview and execute if records were added).
- What's the right error message when the limit is hit? Should include the actual
  count so the user knows how far over they are and can tighten the filter.

---

### Rate limiting between batch updates

**Questions to resolve:**
- What batch size and sleep interval? The roadmap says "pause between batch updates
  to avoid hammering PDI". Concrete proposal: update in batches of 10, sleep 0.5s
  between batches. Configurable via `NOWLINK_BULK_BATCH_SIZE` and
  `NOWLINK_BULK_BATCH_SLEEP` in `.env`.
- Should there be progress reporting? For 500 records this could take ~25 seconds.
  The tool could return intermediate progress if FastMCP supports streaming, otherwise
  just return final count + any failures.

---

### Failure handling in bulk_execute

**Questions to resolve:**
- If 3 out of 500 records fail to update, what happens? Options:
  a) Stop immediately on first failure (safe but all-or-nothing)
  b) Continue and report all failures at the end (more useful, matches how bulk
     operations typically work)
  c) Configurable
- **Recommendation:** Continue and collect failures. Return `{updated: 497, failed: 3,
  failures: [{sys_id, error}, ...]}`. All successful writes still logged. User can
  investigate the 3 failures separately.

### Seed script for PDI test data

The roadmap requires "script to create 20 test incidents" for bulk testing.
**Plan:** Add `scripts/seed_pdi.py` — uses `client.create_record` in a loop to
create 20 incidents with known field values. Run once before bulk testing. Clean up
with a bulk update to Cancelled state after testing.
