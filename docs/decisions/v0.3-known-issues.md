## Pre-flight mandatory field validation — full design history

**Final decision: dynamic validation via sys_db_object + sys_dictionary.**

### Design journey

**v0.2 — hardcoded `TABLE_MANDATORY`**
Covered six known ITSM tables including inherited fields. Broke on custom tables,
required manual maintenance, encoded NowLink's opinion not the instance's configuration.

**v0.3 early attempt — `get_mandatory_fields()` querying `sys_dictionary` directly**
Queried `sys_dictionary` with `mandatory=true` for the target table only.
Missed inherited fields — `short_description` on `incident` is defined on `task`,
invisible when querying `name=incident`.

**v0.3 final — table ancestry walk + sys_dictionary across full chain**
`get_table_ancestry()` walks `sys_db_object` upward via `super_class.name`.
`get_mandatory_fields()` queries `sys_dictionary` with `nameIN{full ancestry}`.
Works for any table on any instance including custom tables.

### Key finding: sys_dictionary.mandatory is not enforced by the REST API

Testing proved that `sys_dictionary.mandatory=true` does not cause the Table API
to reject POSTs. The API accepts creates missing mandatory fields and returns 201.
Setting mandatory=true on `task.short_description` did not block the create.

Observed behaviour when mandatory fields are missing:
- API accepts the request (201) — record created with empty mandatory fields
- Or business rules hang on insert causing a timeout — non-deterministic on PDI
- No `400 Bad Request`. No validation error from ServiceNow.

Additional finding: mandatory enforcement lives on the table where the field is
*defined*, not child tables. Setting mandatory=true on the `incident` entry for
`short_description` has no effect — it must be set on `task`. The ancestry walk
handles this correctly.

### What NowLink's validation actually is

NowLink's pre-flight validation is a UX safety layer, not a prediction of what
ServiceNow will reject. It catches missing fields at preview time — before any
write attempt, before any timeout — and tells the user clearly what's needed.

On a stock PDI (`short_description mandatory=false` on `task`): no validation fires.
Honest — the instance doesn't consider it mandatory via the API.

With `short_description mandatory=true` on `task`: validation fires at preview,
❌ shown to user, write blocked until field is provided.

Newsletter framing: "validate what ServiceNow doesn't."

## Pre-flight mandatory field validation removed

**Decision made during v0.3 build session.**

### What we tried

The plan was to replace the hardcoded `TABLE_MANDATORY` dict with a dynamic
`get_mandatory_fields(table)` function that walks the ServiceNow table inheritance
chain via `sys_db_object` and queries `sys_dictionary` for mandatory fields across
the full ancestry.

The inheritance walk worked — `get_table_ancestry('incident')` correctly returned
`['incident', 'task']`. But `sys_dictionary` returned `mandatory=false` for
`short_description` on `task`, even though the UI treats it as required.

### Root cause

ServiceNow has two separate layers of mandatory enforcement:

1. **`sys_dictionary.mandatory=true`** — database-level. Enforced by the platform
   on every write, including via the REST API. Very few fields are mandatory at this
   level on a standard instance.

2. **UI Policy mandatory** — browser-only. Enforced by JavaScript in the form.
   The REST API has no knowledge of UI Policies. A field can be mandatory in the UI
   and `mandatory=false` in `sys_dictionary` simultaneously.

On a standard PDI, `short_description` on incident is `mandatory=false` in
`sys_dictionary`. It is mandatory in the UI via a UI Policy. The REST API accepts
a POST without `short_description` without complaint.

This was confirmed directly in the ServiceNow platform UI (Table dictionary for
incident, Columns tab, Short description field → Mandatory: false).

There is no reliable API to query UI Policy mandatory rules — `sys_ui_policy` and
`sys_ui_policy_action` exist but are complex, condition-driven, and vary per instance,
per view, and per user. Parsing them reliably is not tractable.

### Decision

Remove pre-flight mandatory validation entirely. `TABLE_MANDATORY` is removed from
`shaper.py`. `get_table_ancestry()` and `get_mandatory_fields()` are not added.
`validate_fields()` in `safety.py` is kept (may be useful in future for explicit
field type checking) but is no longer called by `create_record`.

ServiceNow is the authority on what it accepts. If a create is rejected, the error
comes back from ServiceNow and NowLink surfaces it clearly through Claude. The
confirmation pattern (preview before write) gives the user a chance to review
fields before anything is submitted.

### What this means for custom tables

Custom tables work correctly. If a custom table has genuine database-level mandatory
fields (`sys_dictionary.mandatory=true`), ServiceNow will reject the POST and Claude
will report the error. If mandatory is UI-only, the write will succeed — same
behaviour as any other API client.

### Newsletter note

This became the "Gotcha of the Week" section in the v0.3 newsletter:
"ServiceNow mandatory fields aren't always mandatory via the API."
The distinction between `sys_dictionary.mandatory` and UI Policy mandatory is
something every ServiceNow API developer hits and nobody documents clearly.

## `caller_id` auto-injection kept for incident creates

`create_record` still injects `caller_id` from stored credentials when creating
an incident and the caller is not provided. This is a NowLink product decision,
not a ServiceNow enforcement — it avoids Claude having to ask who the caller is
on every incident create. Overridable by providing `caller_id` explicitly.
