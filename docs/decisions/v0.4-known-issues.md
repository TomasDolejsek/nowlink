# v0.4 — Known Issues & Decisions

---

## There is no direct REST endpoint for triggering Flow Designer subflows

### Finding

`GET /api/now/flow_api` → 400 "Requested URI does not represent any resource"
`GET /api/now/flow_api/flows` → 400 same error

Research confirmed: `flow_api` in the ServiceNow developer documentation refers to
the server-side JavaScript object `sn_fd.FlowAPI`, not a REST namespace accessible
from outside the platform. The path exists in the URL space but requires specific
sub-paths that are not publicly documented as REST endpoints.

### What would work without the bridge

The Flow Designer REST trigger generates a triggerable endpoint automatically — but
this feature requires Integration Hub Enterprise, a paid subscription. Standard PDI
instances show only: Record, Scheduled, Application (Inbound Email, Knowledge
Management, Remote Table Query, Service Catalog, SLA Task).

### Decision

Build a Scripted REST API bridge (`nowlink_flow_bridge`) that NowLink creates on the
instance via the Table API. Its JavaScript calls `sn_fd.FlowAPI` server-side.
This is the standard community workaround for REST-triggerable Flow Designer logic
without Integration Hub.

## Flows cannot accept arbitrary inputs — Subflows can

### Finding

Flows are triggered by conditions (record events, schedules, application events).
They receive context from the trigger — a record, an email, a catalog item — not
arbitrary key-value inputs from an API call.

Subflows have no trigger. They accept declared input variables and return declared
output variables. They are designed for programmatic execution from scripts or
parent flows.

### Decision

v0.4 exposes Subflows only, not Flows. `list_subflows` filters `sys_hub_flow` by
`sys_class_name=sys_hub_subflow`. Tool descriptions tell Claude that if a user
asks to "trigger a flow", check whether it is implemented as a subflow.

Users who want NowLink-triggerable logic should build it as a Subflow in Flow
Designer, not a Flow.

## web_service_admin role required for setup only

### Finding

`nowlink.dev` with `rest_service` only → 403 on `sys_ws_definition`.
After adding `web_service_admin` → 200/201.

### Decision

`web_service_admin` is documented as a setup-time requirement. `nowlink setup-flows`
requires it. Day-to-day subflow triggering uses only the bridge endpoint, which
requires authentication but not `web_service_admin`.

In production deployments the role could be granted for setup and removed after.
NowLink does not require it after the bridge is installed.

### Known issue: timeout error message is misleading

If `setup_flow_bridge()` times out on PDI, the CLI prints:
"Make sure nowlink.dev has the web_service_admin role."

This is misleading — the timeout is a PDI resource issue, not a role problem.
A retry (which hits the idempotency check) will report "already installed" correctly.

Future fix: distinguish `httpx.TimeoutException` from 403 in the CLI error handler
and print appropriate guidance for each.

## execution_id extraction from FlowRunnerResult

### Finding

`String(result)` where `result` is the return value of `.run()` returns
`[object FlowRunnerResult]` — Java object toString(), not the execution ID.

`result.getExecutionId()` returns the sys_flow_context sys_id correctly.
`result.getContextId()` is a fallback for older ServiceNow versions.

### Decision

Bridge script uses `getExecutionId()` with `getContextId()` fallback.
Both are checked with `typeof runner.X === 'function'` guards.

## Flow and Action triggering deferred to v0.5

### Finding

Tested `trigger-flow` with `global.sla_notification_and_escalation_flow` + a real
incident sys_id. ServiceNow returned 500: "The inputs provided to the flow are incorrect."

The bridge script fetches the GlideRecord and passes `current` + `table_name` as inputs.
But flows expect inputs in the exact shape their trigger type provides — a Record trigger
in Flow Designer wires up inputs differently than a manual FlowAPI call does.

The same problem exists for subflows and actions — each declares its own named input
variables. Without knowing what those variables are called, the caller is guessing.

### Decision

`trigger_flow` and `trigger_action` endpoints exist in the bridge but are not exposed
as MCP tools in v0.4. `trigger_subflow` works when the caller knows the correct input
variable names — which is acceptable as a proof-of-concept.

v0.5 will add input variable discovery: query the subflow/flow/action definition to
find declared inputs before triggering, validate what the user provided, and ask for
anything missing. This makes all three trigger types safe to expose as MCP tools.

### Bridge endpoints created

All three endpoints are installed by `nowlink setup-flows`:
- `POST /trigger-subflow` — `.subflow(name).withInputs(inputs).run()`
- `POST /trigger-flow` — `.flow(name).withInputs({current: gr, table_name}).run()`
- `POST /trigger-action` — `.action(name).withInputs(inputs).run()`

They are available for direct HTTP use by developers who know their flow's input
contract. The MCP tools will expose them properly in v0.5.


### Decision

`get_flow_status` is a single GET — it does not retry until Complete.
Tool description explicitly tells Claude: "Do not call this tool in a loop
automatically — always wait for the user to ask for a status update."

Rationale: subflows run asynchronously in the background. Auto-polling from Claude
would create multiple tool calls the user didn't ask for. The user experience is:
trigger → execution_id returned → user asks "is it done?" → Claude calls get_flow_status.

A future version could add a `wait_for_completion` parameter that polls internally
with a configurable timeout, similar to how v0.2 handles POST timeouts.

## output_vars field in sys_flow_context

### Finding

`sys_flow_context.output_vars` field is returned but was empty in all test runs.
The NowLink Test Subflow has an output variable (`result`) set to `"Processed: " + message`,
but `output_vars` came back as an empty string in the API response.

This may be because:
1. Output vars are stored differently in this ServiceNow version
2. The field name is incorrect — other candidates: `outputs`, `output_variables`
3. PDI-specific behaviour

### Decision

Accepted as a known limitation for v0.4. `get_flow_status` returns whatever
`sys_flow_context` provides — if `output_vars` is empty, that's what Claude reports.
Investigating the correct output field is an open question for v0.5.
