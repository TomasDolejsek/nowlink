# NowLink v0.2 — Technical Specification

**Version:** 0.2.0
**Built:** 2026-05-23
**Status:** Complete
**Python:** 3.12+
**Platform:** Windows (tested), macOS (supported)

---

## Overview

v0.2 adds write capability: two MCP tools that let Claude create and update single
ServiceNow records with a mandatory preview-before-write confirmation pattern, field
validation, diff generation, and a write audit log separate from the tool call log.

Core safety principle: every write is a two-step operation. `confirm=False` always
runs first — fetches current state, validates fields, generates a diff — and returns
a preview without touching ServiceNow. `confirm=True` executes the write only after
explicit user approval.

## Module: `safety.py`

Three functions, each with a single responsibility. Designed to be reused by v0.3
bulk operations without modification.

### `validate_fields(proposed, table_schema) -> list[str]`

Checks that all mandatory fields in the schema are present and non-empty in the
proposed dict. A blank string (`"   "`) counts as missing. Returns a list of error
strings — empty list means valid.

Used by `create_record` for unknown tables. Known tables use `TABLE_MANDATORY` directly
(faster, no API call, includes inherited fields).

### `diff_fields(current, proposed) -> dict`

Compares the current shaped record against proposed raw field values. Returns three
buckets:
- `changes` — fields that will change, with `from` (current display value) and `to`
  (proposed raw value)
- `unchanged` — fields where proposed value matches current
- `new_fields` — fields being set that don't exist on the current shaped record

The `from/to` asymmetry is deliberate: `from` is the human-readable display value
(what the user sees now), `to` is the raw code being submitted (what they asked for).

### `log_write(operation, table, identifier, fields_written, diff=None)`

Appends one JSON line per write to `~/.nowlink/logs/writes-YYYY-MM-DD.log`. Separate
from the tool call log — the write log is the audit trail.

Format:
```json
{"ts": "2026-05-23T14:12:01", "op": "update", "table": "incident",
 "record": "INC0000055", "fields": {"priority": "1"},
 "changes": [{"field": "priority", "from": "P3 - Moderate", "to": "1"}]}
```

Creates have no `changes` key. Updates include the full diff.

## Module: `client.py` — New Functions

### `create_record(table, fields) -> dict`

`POST /api/now/table/{table}` with `fields` as JSON body. Returns the created record
(raw, with sys_id and number).

On `httpx.TimeoutException` — calls `_verify_create` before reporting failure.

### `_verify_create(table, fields) -> dict`

Post-timeout verification for creates. Queries the table for a record matching
`short_description` (or first non-system field) created within the last 2 minutes.
Returns the raw record if found. Raises a clear error if not found.

### `update_record(table, sys_id, fields) -> dict`

`PATCH /api/now/table/{table}/{sys_id}` with `fields` as JSON body. PATCH semantics —
only submitted fields are changed, all others untouched.

On `httpx.TimeoutException` — calls `_verify_update` before reporting failure.

### `_verify_update(table, sys_id, fields) -> dict`

Post-timeout verification for updates. Re-fetches the record by sys_id and compares
submitted field values against current ServiceNow raw values. Returns the record if
all fields match. Raises a clear error listing any mismatched fields.

Note: fields recalculated by business rules (e.g. priority from impact+urgency) may
appear as mismatches even when the write was correct. This is ServiceNow's logic.

### `REQUEST_TIMEOUT`

Module-level constant, reads from `NOWLINK_REQUEST_TIMEOUT` in `.env`, defaults to 60.
Applied to all HTTP calls in `client.py`.

## Module: `shaper.py` — Changes

### `TABLE_MANDATORY`

New dict mapping known tables to their mandatory fields, including inherited fields
that `sys_dictionary` misses:

```python
TABLE_MANDATORY: dict[str, set[str]] = {
    "incident": {"short_description", "caller_id"},
    "problem": {"short_description"},
    "change_request": {"short_description", "category"},
    "sc_request": {"short_description"},
    "sc_req_item": {"short_description"},
    "task": {"short_description"},
}
```

`short_description` on `incident` is inherited from `task` — it does not appear in
`sys_dictionary` under `name=incident`, only under `name=task`. This map is the
authoritative source for mandatory field validation for known tables.

**Limitation:** Custom tables (`u_` prefix) have no entry in `TABLE_MANDATORY`.
`create_record` falls back to `sys_dictionary` for these, which misses inherited
mandatory fields. A custom table extending `task` will silently pass validation
without `short_description`, then get rejected by ServiceNow. This is a known
limitation — the fix (dynamic inheritance chain traversal) is planned for v0.3
and will remove `TABLE_MANDATORY` entirely.

## Module: `server.py` — New Tools

### `create_record` tool

**Parameters:**
- `table` — ServiceNow table name
- `fields` — dict of `{field_name: raw_value}`. Values must be raw ServiceNow codes
  (e.g. `"1"` for priority, not `"P1 - Critical"`).
- `confirm` — `False` (default) = preview only. `True` = execute.

**`caller_id` auto-injection:**
If `table == "incident"` and `caller_id` is not in `fields`, the integration user
username is injected automatically from stored credentials. Shown in preview as
`nowlink.dev (auto-filled)`. Overridable by providing `caller_id` explicitly.

**Validation:**
- Known tables: checked against `TABLE_MANDATORY` — fast, no API call, includes
  inherited fields.
- Unknown tables: falls back to `sys_dictionary` via `validate_fields`.

**Confirmation flow:**
```
confirm=False → validate → return preview (no write)
confirm=True  → validate → POST → log_write → return {created, number, sys_id, record}
```

**Returns on preview:**
```json
{"preview": true, "table": "incident", "fields_to_create": {...},
 "validation_errors": [], "message": "Ready to create..."}
```

**Returns on success:**
```json
{"created": true, "table": "incident", "number": "INC0012345",
 "sys_id": "abc123...", "record": {shaped record}}
```

### `update_record` tool

**Parameters:**
- `table` — ServiceNow table name
- `identifier` — record number (e.g. `INC0001234`) or 32-char hex sys_id
- `fields` — dict of `{field_name: raw_value}` — only fields to change
- `confirm` — `False` (default) = preview only. `True` = execute.

**Identifier resolution:**
Fetches the current record first (via `get_record_by_number` or `get_record_by_sys_id`)
to extract sys_id for the PATCH call and to generate the diff. Raises immediately if
sys_id cannot be extracted.

**Confirmation flow:**
```
confirm=False → fetch current → diff → return preview (no write)
confirm=True  → fetch current → diff → PATCH by sys_id → log_write → return result
```

**Returns on preview:**
```json
{"preview": true, "record": "INC0001234",
 "changes": [{"field": "priority", "from": "P3 - Moderate", "to": "1"}],
 "unchanged": [], "new_fields": [], "message": "Ready to update..."}
```

**Returns on success:**
```json
{"updated": true, "record": "INC0001234",
 "changes": [{"field": "priority", "from": "P3 - Moderate", "to": "1"}],
 "result": {shaped record}}
```

### `describe_table` tool — Changes

For tables with a known allowlist in `TABLE_FIELDS`, now returns the allowlist fields
with `TABLE_MANDATORY` for mandatory status — instead of querying `sys_dictionary`.

This is the accurate answer to "what fields does this table have?" — it reflects what
NowLink actually returns, not the full platform schema. Response includes a `source`
field: `"allowlist"` or `"sys_dictionary"`.

Unknown tables still fall back to `sys_dictionary`.

## Write Audit Log

Location: `~/.nowlink/logs/writes-YYYY-MM-DD.log`

Separate from tool call log (`~/.nowlink/logs/YYYY-MM-DD.log`).
One JSON object per line. Append-only. Never deleted by NowLink.

Fields: `ts`, `op` (create/update), `table`, `record`, `fields`, `changes` (updates only).

Currently write-only — no tool to read it. `get_write_log` tool planned for v0.3
alongside bulk operations.

## No Delete — By Design

NowLink will never expose a delete operation. ServiceNow is designed around state:
records are closed, cancelled, and retired — not deleted. Hard deletes bypass business
rules, erase audit history, and break referencing records. From an AI safety
perspective, delete is irreversible — the confirmation pattern works for creates and
updates because field values can be reverted. A deleted record cannot be recovered.

Use `update_record` with state `Cancelled` or `Closed` instead.

## ServiceNow Behaviour Notes

### Priority is calculated, not stored directly

On most ServiceNow instances, priority is auto-calculated from impact and urgency via
a priority lookup rule or business rule. Setting `priority` directly via PATCH gets
immediately overwritten by the calculation. To set priority to P1, set
`impact=1` and `urgency=1` instead.

### PATCH vs PUT

The Table API supports both PUT and PATCH for updates. PUT replaces the entire record
with the submitted payload — any field not included is blanked. PATCH updates only the
submitted fields. NowLink uses PATCH exclusively for all updates.
