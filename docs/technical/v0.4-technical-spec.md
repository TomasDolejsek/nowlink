# NowLink v0.4 — Technical Spec
**Status:** Complete ✅ (proof-of-concept)
**Date:** 2026-06-07

## Status

**Proof-of-concept complete.** Subflow triggering is fully working end-to-end.

The bridge installs three endpoints (`/trigger-subflow`, `/trigger-flow`,
`/trigger-action`) but only one Python client function and one MCP tool are
implemented in v0.4 — `trigger_subflow`. Flow and action triggering are deferred
to v0.5 where input variable discovery will make them safe to expose.

---

## Overview

v0.4 adds three Flow Designer MCP tools (`list_subflows`, `trigger_subflow`,
`get_flow_status`) and a `nowlink setup-flows` CLI command that installs a Scripted
REST API bridge on the ServiceNow instance.

The bridge exposes three endpoints covering all programmatically triggerable Flow
Designer types. Only subflow triggering has a corresponding Python function and MCP
tool in v0.4. Flow and action triggering require input discovery (v0.5) to be safe.

## The Flow Bridge

### Why it exists

`sn_fd.FlowAPI` is a server-side JavaScript API — it exists only inside
ServiceNow's scripting context. There is no direct REST endpoint that exposes it.

The Flow Designer REST trigger (which would auto-generate a triggerable endpoint)
requires Integration Hub Enterprise — a paid subscription. Standard PDI instances
do not have it.

The bridge is NowLink's solution: a Scripted REST API created on the instance via
the Table API. Its scripts call FlowAPI server-side and return the execution context
sys_id to the caller.

### Bridge components

**sys_ws_definition** — the Scripted REST API definition:
```
name:        NowLink Flow Bridge
service_id:  nowlink_flow_bridge
namespace:   x_nowlink
base_uri:    /api/x_nowlink/nowlink_flow_bridge
```

**sys_ws_operation × 3** — three POST resources installed by `setup-flows`:

| Endpoint | FlowAPI call | v0.4 status |
|----------|-------------|-------------|
| `/trigger-subflow` | `.subflow(name).withInputs(inputs).run()` | ✅ Python function + MCP tool |
| `/trigger-flow` | `.flow(name).withInputs({current: gr, table_name}).run()` | Bridge only — v0.5 |
| `/trigger-action` | `.action(name).withInputs(inputs).run()` | Bridge only — v0.5 |

All three return `{status, execution_id}` on success, `{error}` on failure.

### Bridge script (trigger-subflow)

```javascript
(function process(request, response) {
    var body = request.body.data;
    var subflowName = body.subflow_name;
    var inputs = body.inputs || {};

    if (!subflowName) {
        response.setStatus(400);
        response.setBody({ error: 'subflow_name is required' });
        return;
    }

    try {
        var runner = sn_fd.FlowAPI.getRunner()
            .subflow(subflowName)
            .inBackground()
            .withInputs(inputs)
            .run();

        var executionId = null;
        if (runner && typeof runner.getExecutionId === 'function') {
            executionId = runner.getExecutionId();
        } else if (runner && typeof runner.getContextId === 'function') {
            executionId = runner.getContextId();    // older SN versions
        }

        response.setStatus(200);
        response.setBody({
            status: 'triggered',
            subflow_name: subflowName,
            execution_id: executionId,
        });
    } catch (e) {
        response.setStatus(500);
        response.setBody({ error: e.message || String(e) });
    }
})(request, response);
```

`/trigger-flow` and `/trigger-action` follow the same pattern with `.flow()` and
`.action()` respectively. `/trigger-flow` additionally fetches the record via
`GlideRecord` before passing it as `inputs['current']`.

### Role requirement

`nowlink.dev` needs `web_service_admin` to read/write `sys_ws_definition` and
`sys_ws_operation`. Required only during `setup_flow_bridge()`. Not required for
day-to-day subflow triggering or status polling.

## New functions in client.py

### `setup_flow_bridge() → dict`

Creates the bridge on the instance. Fully idempotent — checks both definition and
all three operations before creating anything. Only creates what is missing.

Steps:
1. GET `sys_ws_definition` — check if definition exists
2. If definition missing → POST to create it (with timeout recovery via fresh client)
3. GET `sys_ws_operation` — check which of the three endpoints already exist
4. For each missing operation → POST to create it (with timeout recovery)
5. Return `{"created": bool, "bridge_url": ..., "message": ...}`

Timeout recovery uses a fresh `httpx.Client` — the timed-out client connection
is in a bad state and returns empty results on subsequent calls.

---

### `trigger_subflow(subflow_name, inputs) → dict`

POSTs to `/trigger-subflow` on the bridge.

```python
body = {"subflow_name": subflow_name, "inputs": inputs}
POST /api/x_nowlink/nowlink_flow_bridge/trigger-subflow
```

Returns:
```json
{"status": "triggered", "subflow_name": "global.my_subflow", "execution_id": "abc123"}
```

Raises `RuntimeError` if the bridge returns an error (subflow not found, wrong name).

**v0.5 will add:** `trigger_flow(flow_name, table_name, sys_id)` and
`trigger_action(action_name, inputs)` using the existing bridge endpoints.

---

### `get_flow_status(execution_id) → dict`

GETs `sys_flow_context/{execution_id}` with fields:
`sys_id, name, state, fault_description, output_vars`

State values: `Complete`, `Running`, `Error`, `Cancelled`.

---

### `list_subflows() → list[dict]`

GETs `sys_hub_flow` filtered to:
```
active=true^status=published^type=subflow^ORDERBYDESCsys_updated_on
```

Note: `type=subflow` (not `sys_class_name`) — both flows and subflows share
`sys_class_name=sys_hub_flow`. The `type` field distinguishes them.

Returns list of dicts with `name`, `sys_id`, `description`, `internal_name`,
and `trigger_name` (`scope.internal_name` format, ready for `trigger_subflow`).

## New tools in server.py

### `list_subflows`
Returns count + list. `trigger_name` is pre-formatted for direct use.

### `trigger_subflow`
Parameters: `subflow_name` (str), `inputs` (dict). Returns execution_id immediately.
Tool description: call `list_subflows` first if subflow_name is unknown.

### `get_flow_status`
Parameter: `execution_id` (str). Returns state/name/fault_description.
Tool description: do NOT poll automatically — wait for user to ask.

---

## New CLI command

### `nowlink setup-flows`

Calls `setup_flow_bridge()`. On timeout — retries silently using idempotency check
(fresh client). Distinguishes timeout from role errors in the error message.

---

## Subflow naming

ServiceNow FlowAPI requires `scope.internal_name` format:
- Display name: `NowLink Test Subflow`
- Internal name: `nowlink_test_subflow`
- Scope: `global`
- trigger_name: `global.nowlink_test_subflow`

The internal name is auto-generated by Flow Designer — it is NOT the display label.

---

## Known limitation: input variable names

Each subflow, flow, and action declares its own named input variables. Without
querying the Flow Designer definition, the caller must know the correct variable
names in advance. Passing wrong names causes silent failures — inputs are ignored,
the subflow runs with empty values.

This is why `/trigger-flow` and `/trigger-action` are bridge-only in v0.4.
v0.5 will add input variable discovery before all three trigger types are exposed
as MCP tools.

## PDI notes

- Simple subflows complete within 2–5 seconds on a warm PDI
- `sys_flow_context` is accessible with `rest_service` role only
- `setup_flow_bridge()` POST may timeout on PDI but the write completes — idempotency check and fresh-client retry handle this correctly
- `sys_hub_flow` filter must use `type=subflow` not `sys_class_name=sys_hub_subflow` — both types share the same class name
- Post-timeout verification must use a fresh `httpx.Client` — the timed-out connection returns empty results
