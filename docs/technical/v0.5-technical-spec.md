## Input Discovery

### How it works

ServiceNow does not expose a simple REST endpoint for declared input variables
accessible with standard roles. The data lives in `label_cache` — a JSON field on
both `sys_hub_flow` and `sys_hub_action_type_definition`.

`label_cache` is a JSON array of every variable used in the flow — inputs,
intermediate step outputs, loop variables. The structure is the same for subflows
and actions; only the naming convention differs.

### Subflow inputs

Filter: `var["name"].startswith("subflow.")`

Input name: strip `"subflow."` prefix.
Label: strip `"Input➛"` prefix from `label["label"]`.

```json
{"name": "subflow.message", "label": "Input➛Message", "type": "string"}
→ {"name": "message", "label": "Message", "type": "string"}
```

### Action inputs

Filter: `var["type"] == "action"` and name matches `{{action.X}}`

Input name: extract `X` from `{{action.X}}` via regex.
Exclusions: `_` (empty placeholder), paths with `.` (nested sub-elements), case duplicates.

```json
{"name": "{{action.task}}", "label": "action➛Task", "type": "action", "base_type": "reference"}
→ {"name": "task", "label": "Task", "type": "reference"}
```

### Role requirements

| Table | Required role | Why |
|-------|--------------|-----|
| `sys_hub_flow` | `rest_service` | Inherits from `Flow Block` — no special ACL |
| `sys_hub_action_type_definition` | `flow_designer` | Inherits from `Application File` — developer-tier ACL |

The `Application File` base class carries a read ACL requiring `flow_designer` or
`admin`. This is intentional ServiceNow design — actions are treated as platform
artifacts, same category as scripts and business rules.

## Flow Trigger Logic

### Why flows are different from subflows

Subflows have declared input variables. Flows get their context from their trigger
type — a Record trigger injects the triggering record as `current`, a Schedule
trigger injects timing context. The input contract is defined by the trigger type,
not by the flow developer.

This means:
- Subflows and actions: discoverable inputs, safe to validate, safe to trigger with arbitrary inputs
- Record-triggered flows: can be triggered via bridge by passing a record sys_id
- Non-record flows (scheduled, application trigger): cannot be triggered via API

### trigger_flow logic

```
trigger_flow(flow_name, sys_id="")
  │
  ├─ describe_flow(flow_name) → trigger_context
  │
  ├─ record_triggers = [t for t in trigger_context if t.get("table")]
  │
  ├─ if not record_triggers:
  │     → can_trigger=False, trigger_explanation, alternatives
  │
  ├─ elif not sys_id:
  │     → can_trigger=True, needs_record=True, required_table
  │
  └─ else:
        → trigger_flow_with_record(flow_name, required_table, sys_id)
          → POST /api/x_nowlink/nowlink_flow_bridge/trigger-flow
          → {triggered: True, execution_id: ...}
```

### describe_flow trigger detection

Trigger variables have labels starting with `"Trigger"` and containing `"➛"`.
Two label formats exist:
- `"Trigger➛Task SLA Record"` — direct trigger variable
- `"Trigger - Record Updated➛Versions Record"` — specific trigger type variant

Filter: `label.startswith("Trigger") and "➛" in label and label.count("➛") == 1`

The `count("➛") == 1` check excludes nested trigger path variables like
`"Trigger - Record Updated➛Versions Record➛Document"`.

## New functions in client.py

### `get_subflow_inputs(subflow_name) → list[dict]`

```python
params = {
    "sysparm_query": f"internal_name={internal_name}^type=subflow^active=true",
    "sysparm_fields": "sys_id,name,internal_name,label_cache",
    "sysparm_limit": "1",
}
GET /api/now/table/sys_hub_flow
→ parse label_cache → filter subflow. prefixed vars
```

Returns:
```python
[{"name": "message", "label": "Message", "type": "string"}]
[{"name": "status", "label": "Status", "type": "choice",
  "choices": [{"label": "Active", "value": "active"}]}]
```

### `get_action_inputs(action_name) → list[dict]`

```python
params = {
    "sysparm_query": f"internal_name={internal_name}^active=true^state=published",
    "sysparm_fields": "sys_id,name,internal_name,label_cache,sys_scope.name",
    "sysparm_limit": "1",
}
GET /api/now/table/sys_hub_action_type_definition
→ parse label_cache → filter {{action.X}} vars
```

### `list_actions(limit=50) → list[dict]`

```python
"sysparm_query": "active=true^state=published^ih_action=false^ORDERBYname"
GET /api/now/table/sys_hub_action_type_definition
```

Excludes Integration Hub actions (`ih_action=false`).
Returns `trigger_name` in `scope.internal_name` format.

### `trigger_action(action_name, inputs) → dict`

```python
POST /api/x_nowlink/nowlink_flow_bridge/trigger-action
{"action_name": action_name, "inputs": inputs}
```

Returns `{"status": "triggered", "action_name": ..., "execution_id": ...}`.

### `list_flows(limit=50) → list[dict]`

```python
"sysparm_query": "active=true^status=published^type=flow^ORDERBYname"
GET /api/now/table/sys_hub_flow
```

### `describe_flow(flow_name) → dict`

```python
"sysparm_query": f"internal_name={internal_name}^type=flow^active=true"
GET /api/now/table/sys_hub_flow
→ parse label_cache → filter Trigger➛ vars
```

Returns:
```python
{
    "name": "...",
    "description": "...",
    "trigger_context": [{"name": "...", "label": "...", "type": "...", "table": "..."}],
    "can_trigger_via_api": False,
    "trigger_explanation": "..."
}
```

### `trigger_flow_with_record(flow_name, table_name, sys_id) → dict`

```python
POST /api/x_nowlink/nowlink_flow_bridge/trigger-flow
{"flow_name": flow_name, "table_name": table_name, "sys_id": sys_id}
```

The bridge script fetches `GlideRecord(table_name).get(sys_id)` and passes it as
`inputs['current']` to FlowAPI. Returns `{"status": "triggered", "execution_id": ...}`.

## New and updated tools in server.py

### `describe_subflow`

```
Parameters: subflow_name (str)
Returns: {subflow_name, input_count, inputs: [...], message}
```

### `trigger_subflow` (updated)

Pre-trigger validation added:
1. Call `get_subflow_inputs(subflow_name)`
2. Compare provided inputs against declared inputs
3. Add warnings for unknown keys and missing declared inputs
4. Trigger regardless of warnings (non-blocking)

```python
result["warnings"] = [
    "Unrecognised input(s): text. Declared inputs are: message.",
    "Declared input(s) not provided: message."
]
```

### `list_actions`

Discovery only. Returns trigger_name for each action. Notes that `flow_designer`
role is required.

### `describe_action`

```
Parameters: action_name (str)
Returns: {action_name, input_count, inputs: [...], message}
```

Note: only top-level inputs returned. Nested structured inputs excluded.

### `trigger_action`

Same validation pattern as `trigger_subflow`. Non-blocking warnings. Requires
`flow_designer` role for input discovery.

### `list_flows`

Discovery only. Tool description explicitly states flows cannot be triggered
directly. Directs to `list_subflows` for triggerable automation.

### `describe_flow`

```
Parameters: flow_name (str)
Returns: {name, description, trigger_context, can_trigger_via_api, trigger_explanation}
```

Tool description: `Do NOT use this tool when user asks to trigger — use trigger_flow instead.`

### `trigger_flow`

```
Parameters: flow_name (str), sys_id (str, default "")
```

Three return shapes:

**Non-record flow:**
```python
{"can_trigger": False, "flow_name": ..., "trigger_explanation": ..., "alternatives": ...}
```

**Record flow, no sys_id:**
```python
{"can_trigger": True, "needs_record": True, "required_table": ..., "message": ...}
```

**Record flow, sys_id provided:**
```python
{"triggered": True, "flow_name": ..., "table": ..., "sys_id": ...,
 "execution_id": ..., "message": "Flow triggered successfully. Call get_flow_status..."}
```

## Known limitations

### output_vars still empty

`sys_flow_context.output_vars` returns empty even when a subflow has declared
outputs and they were set during execution. Output variables appear to be stored
in the execution plan JSON at a different path. Not resolved in v0.5.
Carry forward to v0.6 or v1.0.

### flow_designer role for actions

Production deployments need to evaluate whether `flow_designer` on the integration
user is acceptable. It's a developer role — grants read access to all Flow Designer
metadata tables. On PDI: fine. On production: evaluate per security policy.

### native flow_api not used

`POST /api/now/flow_api/flows/{id}/run` requires Integration Hub Enterprise.
The bridge remains the correct path for standard instances. Future: detect
availability and use native endpoint if present.

### Non-record flows not triggerable

Scheduled flows, application-triggered flows: cannot be triggered via API regardless.
The only path is to create the triggering condition naturally (e.g. let the schedule
fire, or rebuild as a subflow).
