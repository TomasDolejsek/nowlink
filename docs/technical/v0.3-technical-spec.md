# NowLink v0.3 — Technical Specification
**Version:** v0.3 — Safe Bulk
**Status:** Complete ✅
**Date:** 2026-05-31

---

## Overview

v0.3 adds safe bulk update operations to NowLink. The core design principle:
Claude must show the user exactly what will change before any bulk write executes,
and the user must explicitly approve in a separate message.

Three new MCP tools: `bulk_preview`, `bulk_execute`, `get_write_log`.
One significant improvement to existing tools: dynamic mandatory field validation
via table ancestry walk, replacing the hardcoded `TABLE_MANDATORY` dict.

---

## New functions — client.py

### `get_table_ancestry(table: str) -> list[str]`

Walks the `sys_db_object` table upward via the `super_class` reference field to
build the full inheritance chain for a given table.

**Algorithm:**
```
current = table
while current not seen:
    ancestry.append(current)
    GET /api/now/table/sys_db_object
        ?sysparm_query=name={current}
        &sysparm_fields=name,super_class.name
        &sysparm_display_value=true
    current = result[0]["super_class.name"] or stop
```

**Key implementation notes:**
- Dot-walk notation (`super_class.name`) works with `sysparm_display_value=true`
  and returns the parent table name as a plain string
- `seen` set guards against circular references
- No try/except inside the loop — errors propagate clearly
- Returns `[table]` if no parent found (base tables)

**Example:** `get_table_ancestry('incident')` → `['incident', 'task']`

---

### `get_mandatory_fields(table: str) -> set[str]`

Returns all mandatory field names for a table including inherited fields.

**Algorithm:**
```
ancestry = get_table_ancestry(table)
GET /api/now/table/sys_dictionary
    ?sysparm_query=nameIN{ancestry_csv}^mandatory=true^active=true^elementISNOTEMPTY
    &sysparm_fields=element
return {r["element"] for r in results}
```

**Important caveat:** `sys_dictionary.mandatory` reflects database-level constraints
only. The ServiceNow REST API does NOT enforce these — the Table API accepts POSTs
missing mandatory fields and returns 201. NowLink's validation is a pre-flight UX
layer, not a prediction of API rejection.

On a stock PDI, `short_description` has `mandatory=false` in `sys_dictionary` even
though it appears mandatory in the UI (enforced by UI Policy, browser-only).

Returns empty set on error — callers handle gracefully (no validation is better
than blocking on infrastructure failure).

---

### `bulk_query(table: str, sysparm_query: str) -> tuple[int, list[dict]]`

Returns total count and 5-record sample for a bulk preview.

**Count mechanism:** `GET` with `sysparm_limit=1` — ServiceNow returns the true
total count in the `X-Total-Count` response header regardless of page size.

**Sample:** Separate `GET` with `sysparm_limit=5&sysparm_display_value=all` for
shaping. Ordered by `sys_updated_on` descending — most recently updated first.

---

### `bulk_fetch_sys_ids(table: str, sysparm_query: str, limit: int = 500) -> list[dict]`

Fetches sys_ids and record numbers for all matching records, bypassing the
`MAX_PAGE_SIZE=50` cap used by `query_records`. Returns minimal fields only
(`sys_id`, `number`) with `sysparm_display_value=false` — sys_ids come back
as plain strings, not display_value dicts.

---

### `bulk_update(table: str, sys_ids: list[str], fields: dict) -> None`

Fires batch PATCH requests in chunks of 50. Sub-request statuses completely ignored.
Outcome verified by caller via post-execute re-count.

**Batch API format:**
```
POST /api/now/v1/batch
{
  "batch_request_id": "nowlink-bulk-{chunk_start}",
  "rest_requests": [
    {
      "id": "0",
      "method": "PATCH",
      "url": "/api/now/table/{table}/{sys_id}",
      "headers": [{"name": "Content-Type", "value": "application/json"}],
      "body": "<base64-encoded JSON of fields>"   ← required by ServiceNow
    },
    ...
  ]
}
```

**Why base64:** ServiceNow Batch API requires request bodies as base64-encoded
JSON strings. Plain JSON dict or string both return `400 Bad Request`.

**Why ignore sub-request statuses:** PDI transaction timeouts return `500
"Transaction cancelled: maximum execution time exceeded"` for sub-requests that
actually completed successfully. On production instances this doesn't occur.
Trusting sub-request statuses gives wrong counts in both directions.

**Chunk sleep:** `NOWLINK_BULK_CHUNK_SLEEP` env var (default 1.0s between chunks).
Reduces PDI load between chunks.

Returns `None`. Callers determine outcome via re-count.

## Session token mechanism — server.py

```python
_bulk_tokens: dict[str, dict] = {}

# Token structure:
{
    "table": "incident",
    "filters": "state=1^caller_id=abc123",
    "fields_to_set": {"impact": "1", "urgency": "1"},
    "count": 42,
    "expires_at": datetime(...)   # now + 5 minutes
}
```

**Properties:**
- Module-level dict — persists across tool calls within same server process
- UUID key — Claude cannot guess or construct a valid token
- Stores all execution parameters — `bulk_execute` reads from stored state,
  not from parameters passed by Claude (Claude cannot tamper with the query)
- 5-minute TTL — forces fresh preview if user delays
- Consumed on use — `del _bulk_tokens[token]` after execute, not reusable

## Tool: bulk_preview

**Input:** `table`, `filters`, `fields_to_set`

**Algorithm:**
1. `client_bulk_query(table, filters)` → count, sample_raw
2. If count > 500: return error with actual count
3. If count == 0: return error
4. Shape sample via `shape_records`, generate before→after diff per record
5. Generate UUID token, store in `_bulk_tokens` with 5-min TTL
6. Return count, sample_with_diff, token, expires_at

**Sample diff format:**
```json
{
  "number": "INC0000001",
  "short_description": "VPN client issue",
  "changes": [
    {"field": "impact", "from": "2 - Medium", "to": "1"},
    {"field": "urgency", "from": "2 - Medium", "to": "1"}
  ],
  "unchanged": []
}
```

**Tool description key instruction:**
"STOP after calling this tool. Do not call bulk_execute automatically."

---

## Tool: bulk_execute

**Input:** `token` (only — no repeated params)

**Algorithm:**
1. Look up token in `_bulk_tokens` — 404 error if missing
2. Check `expires_at` — error if expired, delete expired token
3. `client_bulk_query(table, filters)` — re-count, refuse if > 500
4. `bulk_fetch_sys_ids(table, filters)` — get all sys_ids
5. `client_bulk_update(table, sys_ids, fields_to_set)` — fire batch
6. `client_bulk_query(table, filters)` — post-execute re-count (source of truth)
7. `actually_updated = len(sys_ids) - remaining_count`
8. `log_write(...)` and `del _bulk_tokens[token]`
9. Return `{updated, remaining, message}`

**Tool description key instruction:**
"Only call this when the user has explicitly confirmed after seeing bulk_preview results."

**Why no `confirmed` parameter:** A `confirmed=False` default gave Claude a mechanism
to complete the full operation in one turn by calling `bulk_execute(token, confirmed=True)`
immediately after preview. Removing the parameter forces two separate tool calls
across two conversation turns.

---

## Tool: get_write_log

**Input:** `date` (YYYY-MM-DD, default today), `table`, `record`, `limit` (default 20)

Reads `~/.nowlink/logs/writes-YYYY-MM-DD.log` — JSONL format, one entry per line.
Filters by table and/or record if provided. Returns most recent first.

Log entry format:
```json
{"ts": "2026-05-31T14:32:01", "op": "update", "table": "incident",
 "record": "bulk:state=1:48records", "fields": {...}}
```

## Mandatory field validation in create_record

**Flow:**
```
1. get_mandatory_fields(table)  →  set[str]  (2 API calls: sys_db_object + sys_dictionary)
2. missing = [f for f in mandatory_fields if not fields.get(f, "").strip()]
3. On preview (confirm=False): return missing_mandatory_fields list
4. On execute (confirm=True): block if missing
```

**Fallback:** If `get_mandatory_fields` returns empty set (API inaccessible, no
mandatory fields configured, or stock PDI), no validation fires. Write proceeds.

## Notes on table inheritance model

ServiceNow uses Table Per Hierarchy (TPH) by default for the `task` chain —
`incident`, `problem`, `change_request` and all other task extensions physically
share the same underlying MariaDB table. `sys_db_object.super_class` correctly
reflects the logical inheritance regardless of physical layout.

If NowLink is used against custom tables that use Table Per Class (TPC) or Table
Per Partition (TPP), the `sys_db_object` ancestry walk still works correctly —
it reads the logical schema, not the physical layout. This is why walking
`sys_db_object` is the right approach rather than inferring inheritance from naming
conventions or physical table structure.

**Transaction timeouts:** PDI batch requests time out on sub-requests for
records that were actually updated. This is a PDI resource constraint, not a
production issue. Post-execute re-count handles this correctly.

**Non-deterministic behaviour:** Same request, same PDI state — timeout on one
attempt, success on next. Due to PDI being a shared, resource-constrained environment.
Not reproducible on production instances.

**Bulk record count on PDI:** Reliable up to ~20 records per session. Larger sets
may require multiple preview+execute passes on PDI. No limitation on production.
